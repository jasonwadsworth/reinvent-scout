# Phase 2: map the code, let the user choose topics and goals

## Why

Every precision round on `all` ran into the same limit. The tool can't know which parts of a stack the user cares about, so broad lenses fill up with generic, technically on-stack talks. The fix is to ask the user rather than guess.

1. **Map.** Show the user what the profile found in their code.
2. **Choose.** The user picks a few topics and, for each topic, a goal.
3. **Results.** A short ranked list per choice, each with its `why`.

The existing plain lenses keep working unchanged.

## Vocabulary (user-facing)

| Goal | Lens underneath | Applies to |
|---|---|---|
| **understand** | explain (introductory, level 100/200) | service and pattern topics |
| **go deeper** | all (any level) | service and pattern topics |
| **improve** | fix for a gap topic; next-level for a migration-source pattern (`serverless`, `ecs`, `genai-single-call`) | gap topics and migration sources |

## Target behavior

### 1. `mapProfile(profile, catalog)` in `src/match/map.ts` (domain)

It returns topics in four groups:

- **`services`**: core, then supporting. Platform services are left out, as the lenses already do.
- **`patterns`**: non-gap, non-`dead-code`.
- **`gaps`**: supported gap rules only, with the rule's pillar.
- **`nextSteps`**: migration paths the profile activates, and paths skipped because the profile already has the destination, marked as skipped with the reason.

Each topic carries:

- `id`: a stable string, e.g. `service:Amazon DynamoDB`, `pattern:event-driven`, `gap:gap-no-dlq`, `path:genai-single-call`.
- `label`.
- `note`: one sentence, reusing `why.ts`'s trimming.
- `evidence`: up to 3 `{repo, file, line}`, plus a `more` count.
- `goals`: one entry per applicable goal, `{ goal, sessions: number }`.
  - `sessions` is the number of sessions that goal would return for this topic alone, computed by the same focused matcher as section 2.
  - A goal whose count is 0 is kept and marked `sessions: 0`, so the user sees a dead end instead of picking it.

Order topics within each group the same way `concepts.ts` orders them, i.e. by centrality.

### 2. Focused matching: `matchFocus(profile, focus, catalog, options)` in `src/match/focus.ts`

- **Input.** `focus` is `[{ topic: <id>, goal: "understand" | "deepen" | "improve" }]`, 1–6 entries.
  - An unknown topic id is a `ValidationError` that names the id and lists the valid ones.
  - A goal that isn't applicable to the topic is also a `ValidationError`.
- **Per entry.** Run the underlying lens restricted to that one topic:
  - understand / deepen: only sessions admitted by that concept.
  - improve on a gap: only that fix rule.
  - improve on a path: only that next-level rule.

  Reuse the existing admission, demotion and ranking. Don't fork them.
- **Output.** `{ results: [{ topic, goal, candidates, uncovered? }] }`, with candidates capped at `perTopic` (default 5, max 10).
  - Every candidate keeps its full `why`.
  - A session that appears under more than one entry is listed under its first (highest-priority) entry only, and later entries note `alsoMatches`.
  - An entry with no candidates says why, reusing explain's `uncovered` reasoning or the fix/next-level empty reasons.

### 3. Adapters (thin)

- **CLI.**
  - `reinvent-scout profile map --profile <file|name> [--json]`: a readable grouped list showing each topic's id, note, evidence and `goal (N sessions)`.
  - `reinvent-scout match --profile … --focus "<id>:<goal>,<id>:<goal>" [--per-topic N] [--json]`.
  - For the CLI only, `<id>` may also be the bare label ("DynamoDB", "gap-no-dlq") when it's unambiguous.
- **MCP.**
  - New tool `map_profile({ profile })`.
  - `match_sessions` gains an optional `focus` argument (mutually exclusive with `lens`, and a `ValidationError` if both are given).
  - The 30 KB budget must hold with the maximum focus entries and per-topic count.
  - CLI `--json` equals the MCP object.

### 4. Skill flow

Update SKILL.md and workflow.md so the default recommendation flow is: profile → validate → `map_profile` → present the map → ask what the user cares about → `match_sessions` with `focus`.

- **Presenting the map:** group by section, one line per topic, plus the goals that have sessions.
- **Asking:** ask the user to pick up to ~5 topics and a goal for each, in plain words, e.g. "understand DynamoDB, improve the dead-letter gap".
- **Presenting results:** grouped per choice, each session leading with its `why`.
- **Fallback:** if the user just wants recommendations without choosing, fall back to a plain lens as today.

Update the pinned content tests.

## Evaluation

For hallway, kirocrew, adaptative-http and policy-tracker:

1. Run `profile map`.
2. Pick 4 realistic choices per profile, covering at least one of each goal where available. Choose them from the map alone, before looking at any results.
3. Run `match --focus`. Grade each candidate GENUINE/WEAK/NOISE for *that topic and goal*, using the strict rubric style from `2026-09-30-all-lens.md`.
4. Record the choices in the plan Results so the reviewer can re-run them.

## Targets

- **Focused precision:** ≥80% GENUINE across all focused results, since focusing should make results much more precise than `all`. The reviewer re-grades independently.
- **Counts:** every `sessions` count in the map equals the number `matchFocus` returns for that single topic and goal (a test proves it).
- **No regressions:** existing lenses are byte-identical to main on all 7 profiles, and the MCP budget holds.
