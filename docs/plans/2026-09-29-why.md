# Phase 2: tell the user why each session is recommended

## Why

The match output doesn't explain itself.

- **Generic reasons.** The reasons are the rule's generic text ("dead-letter handling is not evident in the cited scope"), a strength number, and ranking internals ("Text overlap on: …", "Uses Amazon Bedrock, which this session covers").
- **Specifics already exist but are dropped.** The profile already holds the specific, human-written gap note ("the three tenant-lifecycle EventBridge rules targeting Step Functions set no deadLetterQueue…") and the concept's evidence. The session's abstract holds the sentence that actually matched. Neither reaches the user.
- **Misleading secondary reasons.** A secondary ranking reason sits next to the real one and misleads. A user read "Uses Amazon Bedrock" on a broad-IAM result and concluded the tool was confused.

## Target behavior

Every candidate, under every lens, carries a `why` object, built deterministically in the domain (no model text). The CLI and MCP output match, and every part below comes from the profile or the session.

```json
"why": {
  "summary": "Covers your gap-no-dlq: the three tenant-lifecycle EventBridge rules targeting Step Functions set no deadLetterQueue or retry policy.",
  "yourCode": [{ "repo": "policy-tracker", "file": "…/tenant-created/cdk-construct.ts", "line": 179 }],
  "sessionSays": "…using dead-letter queues and redrive to recover from failed event deliveries…"
}
```

### `summary`: one sentence per lens

| Lens | Summary text |
|---|---|
| **fix** | `Covers your <gap>: <the gap pattern's note>`. If there is no note, fall back to the rule's plain-language description: which pillar, and what's missing. |
| **next-level** | `Next step from <source pattern> (<pattern note or evidence note>) toward <destination>.` |
| **explain** | `Explains <concept>, which this code uses <service usage or pattern note>.` If there is no note, say "at `<file>:<line>`". |
| **all** | `Matches your <strongest 1-2 services or patterns by reason weight>`, with that concept's usage note when it has one. |

- Trim notes to one sentence, at most about 200 chars. Strip the profiling-guide boilerplate prefix "Not evident in the cited scope:".
- When more than one rule admitted the candidate (fix/next-level), the summary names the first rule and adds `(+N more)`. The other rules keep their full reasons.

### `yourCode`

- Up to 3 citations for the concept or gap in the summary, as `{repo, file, line}`.
- Deduped and in profile order.
- Include a `more` count when citations were cut.

### `sessionSays`

- The sentence of the session's title or abstract that contains the matched phrase: the lens phrase, or the concept or service name.
- Preference order: the first unlisted mention in the abstract, then in the title (the whole title), then the first *listed* mention in the abstract, then in the title. A session that names the service only inside a list is still recommended, and a real quote that shows it only appears in a list tells the user how thin the match is. Trim to about 160 chars around the match with ellipses.
- Never invent text. Omit the field (never leave it empty) only when there is no mention at all.

### Display

- **CLI human output:** show `why` first, under the title line, as `Why:` / `Your code:` / `Session:`.
- **Ranking reasons:** kind `service`, `topic`, `text`, `area` and similar stay in JSON `reasons`, but the human output drops them unless `--verbose` is passed. Add `--verbose`; it's a CLI display flag only.
- **Lens reasons:** `pillarGap`, `migrationPath` and `explainsConcept` reasons stay in human output, after `why`, because they carry every source.
- **Skill:** update SKILL.md step 6 and workflow.md so the agent leads each candidate with `why.summary` plus `sessionSays`, cites `yourCode`, and doesn't read out ranking reasons unless asked. Update the pinned content tests.

### MCP

- The 30 KB budget must still hold at the max limit with `why` included. Test it.
- Budget order when trimming: `sessionSays` survives, and the ranking reasons are dropped first.

## Rules

- **Domain logic** lives in `src/match/**`, in a new `why.ts`. The CLI and MCP only format it. `response.ts` stays the shared builder.
- **Tests:** TDD with synthetic records and profiles. Sabotage each part (summary per lens, note trimming and prefix strip, citation cap and dedupe, sentence extraction, title case, the listing skip, omission when nothing can be quoted, human-output ordering, `--verbose`) and confirm a named test goes red.
- **No regressions:** candidate order and membership must be unchanged on all 7 eval profiles under all 4 lenses. Diff the codes.
- **Types:** `exactOptionalPropertyTypes` applies. Omit keys, never write undefined.

## Acceptance (the reviewer checks by reading)

Take hallway, adaptative-http and policy-tracker, all 4 lenses, and the top 5 of each. That's 60 candidates.

- `summary` must be true of the code at `yourCode`.
- `sessionSays` must be a real quote from that session and on-topic for the summary.
- The target is at least 95% of candidates. List every failure.

## Out of scope

- Ranking changes.
- The `all` lens precision.
- Model-written prose.

## Results

Implemented on `phase-2/why`, seven commits on top of 544332b. `npm run check` is green on every commit; final suite is 1271 tests.

### What shipped

- `src/match/why.ts` builds `why` for every candidate under all four lenses. `match.ts` attaches it (`MatchCandidate.why` is required); `response.ts` adds it to the lean candidate, so the CLI `--json` and the MCP `match_sessions` return the same object.
- `lens-signals.ts` hits now carry the match site (title or abstract, offset, length) and the destination. `explain.ts` matches carry a site and concepts carry the profile's usage or note. `mentionsOf` is the one mention finder, shared by the explain lens and the quotes, so a quote never comes from inside an enumeration (including the "Lambda, DynamoDB & SQS" form).
- CLI human output: `Why:` / `Your code:` / `Session:` directly under the title line, then `Rules:`, then lens reasons. Ranking reasons appear only under `--verbose`. `--verbose` is a display flag and does not change `--json`.
- MCP budget order: if the response does not fit, every candidate's ranking reasons are dropped first (`rankingReasonsOmitted: true`), then whole candidates. `why` and its `sessionSays` are never trimmed. Tested at the maximum limit for all four lenses.
- SKILL.md step 6 and "Presenting reasons and evidence", workflow.md (example, field docs, step 6, CLI paragraph) and the README are updated, with pinned content tests.

### Decisions made during implementation

1. **Fix and Next-level name the strongest rule, not the first.** The plan says "first rule"; with several rules admitting a session the first in rule order can be the weakest, and then the quote (from the strongest hit) would not match the summary. Ties go to rule order. The others are still counted as `(+N more)` and keep their full reasons.
2. **`all` lens naming.** Top two service or topic reasons by weight, note on the strongest. If neither is named in the session's title or abstract, a weaker matched concept, else any non-gap service or pattern of the profile that the session does name (title first), takes the second place, so the summary and the quote are about the same thing. Without this 7 of the 20 `all` candidates in the read had no quote. A session matched only by an area of interest or shared wording says "Matches your interest in X" / "Matches the wording of your profile: ..." and cites no code.
3. **`yourCode` under `all`** interleaves the two named concepts' citations (first, second, first ...), capped at 3.
4. **Notes** are cut at the last clause break (`, ` or `; `) past the midpoint of the 200-character cap, never inside an open parenthesis. A note set inside parentheses (next-level, `all`) has its own parenthetical asides removed so parentheses never nest. A trailing acronym in a catalog name ("Amazon Simple Queue Service (Amazon SQS)") is dropped in summaries.
5. **Explain summary** reads `Explains <concept>, which this code uses: <note>.` (colon), because usage notes are noun phrases. Without a note: `... which this code uses at <file>:<line>.` with the repo in front when the profile spans several.
6. **Ranking is untouched.** Diffed against 544332b on all 7 profiles under all 4 lenses at `--limit 100`: 28 of 28 cells identical in candidate order, scores, reasons, lensRules, skippedRules and uncovered. Only `why` is new.
7. `--verbose` and `rankingReasonsOmitted` are additions to the plan's surface, needed for the display rule and the budget order. Two existing MCP tests changed with the contract: the lean-shape key list now includes `why`, and the default-limit rich-profile case now fits after ranking reasons are dropped (no candidate omitted) where before it truncated.

### Sabotage

Each of these was removed or defeated and a named test went red: note prefix strip, first-sentence split, 200-character cap, clause cut, open-parenthesis guard, aside removal (and its recursion); quote sentence boundaries, newline boundary, 160-character window and ellipses; citation dedupe, cap of 3, `more`, absent `line`; strongest-rule choice and `(+N more)`; fix fallback description; next-level evidence note and destination; explain note and location fallback, repo prefix, taken concept, ampersand offset mapping; `all` weight order, dedupe, two-concept cap, swap-in of a quotable concept, gap exclusion, title-first, citation interleave, pattern wording and name fallbacks, interest and wording fallbacks; title-versus-abstract quote; listing skip; the abstract reaching the quote; human-output ordering, `--verbose`, `Your code` and `Session` omission, `+N more`; ranking-reason budget stage and the reason-kind predicate; `why` in the lean candidate.


### Follow-up: abstract quotes, less duplication in the table

Two commits after the results above (a173f96, 6bc3a3d); 1276 tests.

1. **`sessionSays` prefers the abstract.** The quote is the first unlisted abstract sentence holding the matched phrase, concept or its short name; the title only when the abstract has no such sentence (for example COP311, whose abstract says "cost management" where the fix rule wants "cost allocation"). Applied to fix and next-level (the hit site is the abstract match when there is one), explain (the concept's abstract mention), and `all` (abstract site first; among the two named concepts the one the abstract says is quoted; a swapped-in concept prefers the abstract too). Tests: a fix, an explain and an `all` record with both a title and an abstract match must quote the abstract sentence; a title-only and a listed-only abstract fall back to the title. Sabotaged (each red on a named test): fix abstract-over-title, its `inTitle` flag, the explain choice, the `all` site order, the named-concept preference, the swap-in sort.

Every reason, lens and ranking, with its `Source:` lines, is behind `--verbose`. JSON and MCP are unchanged apart from the quote. Sabotaged: the reasons gate goes red on two named CLI tests.
