# Phase 2: tell the user why each session is recommended

## Why

The match output doesn't explain itself.

- **Generic reasons.** The reasons are the rule's generic text ("dead-letter handling is not evident in the cited scope"), a strength number, and ranking internals ("Text overlap on: …", "Uses Amazon Bedrock, which this session covers").
- **Specifics already exist but are dropped.** The profile already holds the specific, human-written gap note ("the three tenant-lifecycle EventBridge rules targeting Step Functions set no deadLetterQueue…") and the concept's evidence. The session's abstract holds the sentence that actually matched. Neither reaches the user.
- **Misleading secondary reasons.** A secondary ranking reason sits next to the real one and misleads. A user read "Uses Amazon Bedrock" on a broad-IAM result and concluded the tool was confused.

## Target behavior

Every candidate, under every lens, carries a `why` object, built deterministically in the domain (no model text). The CLI and MCP output match, and every part below comes from the profile or the session.

```json
"why": {
  "summary": "Covers your gap-no-dlq: the three tenant-lifecycle EventBridge rules targeting Step Functions set no deadLetterQueue or retry policy.",
  "yourCode": [{ "repo": "policy-tracker", "file": "…/tenant-created/cdk-construct.ts", "line": 179 }],
  "sessionSays": "…using dead-letter queues and redrive to recover from failed event deliveries…"
}
```

### `summary`: one sentence per lens

| Lens | Summary text |
|---|---|
| **fix** | `Covers your <gap>: <the gap pattern's note>`. If there is no note, fall back to the rule's plain-language description: which pillar, and what's missing. |
| **next-level** | `Next step from <source pattern> (<pattern note or evidence note>) toward <destination>.` |
| **explain** | `Explains <concept>, which this code uses <service usage or pattern note>.` If there is no note, say "at `<file>:<line>`". |
| **all** | `Matches your <strongest 1-2 services or patterns by reason weight>`, with that concept's usage note when it has one. |

- Trim notes to one sentence, at most about 200 chars. Strip the profiling-guide boilerplate prefix "Not evident in the cited scope:".
- When more than one rule admitted the candidate (fix/next-level), the summary names the first rule and adds `(+N more)`. The other rules keep their full reasons.

### `yourCode`

- Up to 3 citations for the concept or gap in the summary, as `{repo, file, line}`.
- Deduped and in profile order.
- Include a `more` count when citations were cut.

### `sessionSays`

- The sentence of the session's title or abstract that contains the matched phrase: the lens phrase, or the concept or service name.
- Use the first unlisted match. Trim to about 160 chars around the match with ellipses.
- If the match was in the title, use the title.
- Never invent text. If nothing can be quoted, omit the field. Don't leave it empty.

### Display

- **CLI human output:** show `why` first, under the title line, as `Why:` / `Your code:` / `Session:`.
- **Ranking reasons:** kind `service`, `topic`, `text`, `area` and similar stay in JSON `reasons`, but the human output drops them unless `--verbose` is passed. Add `--verbose`; it's a CLI display flag only.
- **Lens reasons:** `pillarGap`, `migrationPath` and `explainsConcept` reasons stay in human output, after `why`, because they carry every source.
- **Skill:** update SKILL.md step 6 and workflow.md so the agent leads each candidate with `why.summary` plus `sessionSays`, cites `yourCode`, and doesn't read out ranking reasons unless asked. Update the pinned content tests.

### MCP

- The 30 KB budget must still hold at the max limit with `why` included. Test it.
- Budget order when trimming: `sessionSays` survives, and the ranking reasons are dropped first.

## Rules

- **Domain logic** lives in `src/match/**`, in a new `why.ts`. The CLI and MCP only format it. `response.ts` stays the shared builder.
- **Tests:** TDD with synthetic records and profiles. Sabotage each part (summary per lens, note trimming and prefix strip, citation cap and dedupe, sentence extraction, title case, the listing skip, omission when nothing can be quoted, human-output ordering, `--verbose`) and confirm a named test goes red.
- **No regressions:** candidate order and membership must be unchanged on all 7 eval profiles under all 4 lenses. Diff the codes.
- **Types:** `exactOptionalPropertyTypes` applies. Omit keys, never write undefined.

## Acceptance (the reviewer checks by reading)

Take hallway, adaptative-http and policy-tracker, all 4 lenses, and the top 5 of each. That's 60 candidates.

- `summary` must be true of the code at `yourCode`.
- `sessionSays` must be a real quote from that session and on-topic for the summary.
- The target is at least 95% of candidates. List every failure.

## Out of scope

- Ranking changes.
- The `all` lens precision.
- Model-written prose.
