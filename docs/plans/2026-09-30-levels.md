# Phase 2: let the user ask for a session level

## Why

A user should be able to say "I only want 400–500 sessions" (or "nothing introductory", or "300 and up") and have every recommendation honor it.

Today:
- `catalog search --level 100-300` filters by level.
- Matching (the lenses, `map_profile` and focus) has no level control.
- The only level rule is explain/understand's fixed 100/200.

Catalog levels: 100 (76), 200 (323), 300 (1210), 400 (405), 500 (28), unknown (1).

## Target behavior

1. **One option, everywhere.**
   - `levels?: LevelBandRange` (`{min, max}`, the existing type in `src/catalog/query.ts`) is accepted by:
     - `matchSessions` (every lens)
     - `matchFocus`
     - `mapProfile`
   - Reuse the existing semantics: inclusive range, and a session with no level band is excluded when a filter is set (same as `catalog search`).
   - Validate: `min ≤ max`, values in {100,200,300,400,500}.
2. **Filtering doesn't change ranking.**
   - Apply the filter after admission and ranking. The remaining sessions keep their relative order.
   - The 3-per-concept cap and the focus dedupe operate on the filtered list, so the top 10 is filled from in-range sessions.
3. **Map counts respect the filter.**
   - `mapProfile` counts each goal under the filter, so the map shows what's actually available at the user's level.
   - A goal that has sessions outside the range but none inside gets a reason, e.g. "6 sessions, none at 400–500".
4. **Explain/understand intersect, they don't override.**
   - Understand stays introductory (100/200) intersected with the filter.
   - If the intersection is empty (e.g. 400–500), then:
     - `--lens explain` is a `ValidationError`: "explain lists introductory (100–200) sessions, which is outside 400–500; use deepen or all".
     - In the map and focus, understand shows 0 with that reason rather than being hidden.
   - Explain's `uncovered` "closest 300-level" hint is suppressed when 300 is outside the filter.
5. **Empty results explain themselves.**
   - When the filter empties a lens result or a focus choice that would otherwise have sessions, say so with the count: "4 sessions match, none at 400–500".
6. **The response echoes the filter.**
   - Every match, focus and map response includes `levels` when a filter was applied, so the agent can state it.
   - `why` is unchanged.
7. **Adapters.**
   - CLI: `--level <band>`, reusing `parseLevelBandRange` from `catalog.ts` (move it to a shared place), on `match` and `profile map`.
   - MCP: `levels: {min, max}` on `match_sessions` and `map_profile`.
   - CLI `--json` equals MCP, and the budget holds.
8. **Skill.**
   - SKILL.md and workflow.md tell the agent to pass `levels` whenever the user states a level preference, in numbers or words, and to keep it for the rest of the conversation, including the map.
   - Word mapping, from the catalog's own labels:
     - 100 Foundational
     - 200 Intermediate
     - 300 Advanced
     - 400 Expert
     - 500 Distinguished
   - "advanced and up" = 300–500, "expert" = 400–500, "no intro" = 300–500.
   - When the filter empties something, the agent says so rather than silently widening it. It may offer to widen.
   - Update the pinned content tests.

## Tests and checks

- TDD with sabotage for each numbered item.
- **No regressions:** with no `levels`, all four lenses, `map_profile` and focus are byte-identical to main on all 7 eval profiles (`<scratchpad>/gaps/`).
- **With `levels` 400–500:**
  - Every returned session is 400 or 500.
  - The order matches the unfiltered order restricted to 400/500.
  - The map counts equal the focus totals under the same filter (extend the existing count test).
- MCP stays under the 30 KB budget.

## Out of scope

Ranking changes, persisting preferences, and the small e2e-test fixes (a separate PR).

## Results

Two commits on `phase-2/levels`: levels (`preferences.levels`), then session types (`preferences.formats`). `npm run check` is green on each; 1498 tests (1434 on main).

**What was built.** One `SessionPreferences` object (`src/match/preferences.ts`) taken by `matchSessionsDetailed`, `matchFocus` and `mapProfile` (CLI `--level`, `--prefer`, `--avoid`, `--exclude` on `match` and `profile map`; MCP `preferences` on `match_sessions` and `map_profile`). Levels and `exclude` are applied to the index before admission scoring, in the three places that iterate it (`explainSessions`, `allRanked`, `rulesRanked`), while corpus statistics, vocabularies and the stack-fit catalog stay those of the whole catalog, so a session's score does not move. `prefer`/`avoid` is a tier: a key after the demotion partition in `rankAll` (the All lens) and a stable sort of the final list in every other lens, the explain selection and the focus goals. A `why` summary names the rule. The response echoes `preferences` (type names as the catalog spells them) and a `reason` says "N sessions match, none at 400–500" (or "after excluding ...") when the preferences emptied a result that has sessions. Explain and understand intersect with 100–200, and refuse (lens) or show 0 with the reason (map, focus) when the intersection is empty; the "closest 300-level" hint is dropped when 300 is outside the range.

**Regression, no preferences.** `all`, `explain`, `fix`, `next-level` (`--limit 100`, JSON with abstracts), `--verbose` text, `profile map` (JSON and text) and a focus (the recorded picks, `--per-topic 10`, JSON and `--verbose`) are byte-identical to main (99b94f0) on all 7 profiles: 70/70 comparisons.

**400–500, 7 profiles.** Every returned session is 400 or 500 in all three list lenses (21 lists) and in every focus choice: 0 violations. The map count equals the focus total for every topic and goal under the same range: 258/258. Order: `fix` and `next-level` match the unfiltered order restricted to 400/500 exactly. The All lens does not, on 5 of 7 profiles, and this is plan item 2 doing its job: the filter is applied before the 3-per-concept cap, so the cap fills the first places from in-range sessions and moves the fourth session of a concept behind other concepts' sessions, where the unfiltered list had it ahead. Item 2 and the "same order as unfiltered" check cannot both hold for the All lens; I followed item 2, and the test `applies the per-concept cap to the sessions in range` pins it (it goes red if the filter is moved after the cap).

**Session types, Jason's example** (`--prefer "chalk talk" --avoid "breakout session@300-500"`), 7 profiles x 4 lenses = 28 lists: every chalk talk is ahead of every neutral session and every avoided breakout is behind them (28/28); demoted sessions stay last (28/28); a breakout at 100–200 is neutral and keeps its place. Within a tier the unfiltered order is kept in 22/28; the 6 that differ are the All lens again, because the per-concept cap runs after the tier, as the plan says.

**Decisions.**
- The tier is a sort key after the demotion partition in the All lens (demoted sessions are partitioned last after sorting, so the key's position relative to `demoted` cannot change a result; the mutation that swaps them is an equivalent mutant).
- Explain: a stable sort of the selected sessions by tier, not a tier in the round-robin. Putting the tier in the selection comparator changes nothing once the final list is sorted.
- Types resolve by exact name (any case) before a unique prefix, in both the CLI and MCP, and an unknown or ambiguous type is an error naming the catalog's types.
- CLI rules keep the order typed across `--prefer`, `--avoid` and `--exclude`; they are parsed when read, inside the command's own error handling, so a bad `@band` is a printed error and exit 1.
- With a range set, the text map's empty-goal lines say "at level 400–500" instead of "in the catalog", and name the introductory limit for `understand`.

**Sabotage.** 31 level mutants and 33 format mutants, each red on a named test. Three were green and fixed (singular "1 session matches", the response `reason`, the trimmed map's echoed preferences), four format mutants were green and fixed with tests (exact name before prefix, "an exam prep", focus `why`, the explain and understand tier sorts), and the equivalent mutant above is the only one left. Two redundant pieces of code the mutants exposed (a tier in the explain comparator and in the explain input) were removed instead of tested.

## Scope extension (Sep 30): session preferences, not just levels

Jason wants to tell the agent things like "chalk talks more than anything, and avoid breakout sessions unless I'm doing introductory level", the same way as the level range. That makes `levels` one part of a general `preferences` object, and the rest of this plan applies to all of it:

```ts
interface SessionPreferences {
  levels?: LevelBandRange;              // as above: a hard filter
  formats?: FormatRule[];               // applied in order; for a given session, the first rule that matches wins
}
interface FormatRule {
  type: string;                         // a catalog session type, validated against the catalog vocabulary (case-insensitive)
  action: "prefer" | "avoid" | "exclude";
  levels?: LevelBandRange;              // the rule only applies to sessions in this range
}
```

The catalog has these types: Chalk talk 639, Breakout session 477, Workshop 290, Builders' session 243, Lightning talk 208, Code talk 118, Gamified learning 26, Lab 22, Bootcamp 16, Exam prep 4.

"Chalk talks more than anything, avoid breakouts unless introductory" becomes:
`formats: [{type:"Chalk talk", action:"prefer"}, {type:"Breakout session", action:"avoid", levels:{min:300,max:500}}]`.

The three actions:

- **exclude**: the session is removed, the same as a level filter.
- **prefer / avoid**: a new rank tier, placed after the existing demotion tier and before every other key. The order is not-demoted, then preferred > neutral > avoided, then the lens's existing order.
  - "More than anything" means a preferred-format session outranks a neutral one in the same lens result, even one that matches more strongly.
  - Within each tier, the existing order is kept.
  - The 3-per-concept cap and focus dedupe run after this tier.
- **why**: a preferred session's summary gets "(a chalk talk, which you prefer)". An avoided one gets "ranked lower: a breakout session, which you asked to avoid at 300–500".

Format rules apply to every lens and focus goal, including explain/understand. Explain's own built-in breakout/chalk bonus remains a tiebreak inside the tiers.

Map counts respect `exclude` and `levels`, because those remove sessions. They don't change for prefer/avoid, because those only reorder.

On the adapters, the MCP `preferences` object goes on `match_sessions` and `map_profile`. The CLI gets:
- `--level <band>`
- `--prefer <type>[@<band>]`, repeatable
- `--avoid <type>[@<band>]`, repeatable
- `--exclude <type>[@<band>]`, repeatable

For example, `--prefer "chalk talk" --avoid "breakout session@300-500"`. Format names are case-insensitive, and a unique prefix is enough ("chalk").

The skill should turn plain statements into `preferences` and keep them for the rest of the conversation. Examples to document:

| User says | Preference |
|---|---|
| "only 400+" | levels 400–500 |
| "no workshops" | exclude Workshop |
| "I like chalk talks" | prefer Chalk talk |
| "avoid breakouts unless intro" | avoid Breakout session at 300–500 |

The agent restates the active preferences once, briefly, when it applies them, and says when a preference empties a result. Format synonyms are documented: chalk talk, breakout or talk, workshop, builders' session, lightning talk, code talk, lab, bootcamp.

Additional checks:
- With Jason's example on all 7 eval profiles, every chalk talk is ahead of every non-chalk in each lens result, every breakout at 300+ is behind the neutral sessions, and breakouts at 100–200 are untouched.
- No preferences gives output byte-identical to main.
- Each rule part is TDD-tested with sabotage: type match, level-scoped rule, first-match-wins, the three actions, and why text.

## Scope extension 2 (Sep 30): any catalog facet, plus discovery

Jason also wants to say "focus on a specific venue", and to ask what he can filter on, e.g. "list the venues" or "what categories are there". So format rules generalize to facet rules, and a discovery tool lists the available values.

```ts
interface SessionPreferences {
  levels?: LevelBandRange;
  rules?: FacetRule[];
}
interface FacetRule {
  field: "format" | "venue" | "day" | "topic" | "area" | "industry" | "role";
  value: string;                        // validated against that field's catalog vocabulary, case-insensitive, unique prefix allowed
  action: "only" | "prefer" | "avoid" | "exclude";
  levels?: LevelBandRange;              // the rule applies only to sessions in this range
}
```

`format` replaces the earlier `formats` list. Fields map to `IndexRecord` as follows:

| Field | IndexRecord field |
|---|---|
| format | `type` |
| venue | `venue` |
| day | `startDate` |
| topic | `topics` |
| area | `areasOfInterest` |
| industry | `industries` |
| role | `roles` |

The multi-valued fields (topic, area, industry, role) match when any of the session's values match.

### Semantics

- **`only`**: an include filter. Several `only` rules on the same field combine as a union, for example "MGM Grand or Wynn/Encore". `only` rules on different fields combine as an intersection.
- **`exclude`**: removes the session.
- **Missing values**: a session with no value for a field that has an `only` rule is removed. This mirrors the level rule. 47 sessions have no venue.
- **`prefer` / `avoid`**: within one field, the first matching rule decides. Across fields, the effects add up (+1 for prefer, −1 for avoid). The tier is the sum, highest first. It sits after the demotion tier, as the earlier extension describes.
- **Map counts**: they respect `only`, `exclude` and `levels`.
- **`why`**: names every preference that moved the session, for example "(a chalk talk at MGM Grand, which you prefer)".

### Discovery

- **The tool**: add `listFilters(catalog)` to `src/catalog/**`, exposed as a new MCP tool `list_filters` and a new CLI command `catalog filters [--field <f>] [--json]`.
- **What it returns**: for every field above, plus `level`, each value with its session count, sorted by count. Distinct talks count once; repeats don't.
- **Read-only**: it needs no profile and no sign-in.
- **The skill**: when the user asks what they can filter on, or names a value that doesn't resolve, the agent calls `list_filters`. A misspelled venue or format becomes a ValidationError that lists the closest valid values.

### CLI

- `--only <field>:<value>[@<band>]`, repeatable.
- `--prefer`, `--avoid` and `--exclude` take `[<field>:]<value>[@<band>]`. When no field is given, it defaults to `format`.
- Examples:
  - `--only venue:mgm`
  - `--prefer chalk --avoid "breakout@300-500"`
  - `--exclude topic:"Migration & Modernization"`

### Skill wording to document

| User says | Rule |
|---|---|
| "only sessions at MGM" | `only` venue MGM Grand |
| "I'm staying at the Venetian, prefer sessions there" | `prefer` venue Venetian |
| "nothing on Thursday" | `exclude` day <that date> |
| "what venues are there?" | call `list_filters` with field venue |

### Additional checks

- **`only venue:MGM Grand`**: every result on all 7 profiles is at MGM Grand. The map counts drop to match, and the focus totals equal the map counts.
- **Combining rules**: union within a field and intersection across fields are tested. Each is sabotaged to confirm the test fails.
- **`list_filters`**: its counts are tested against a fixture, and it must stay within the MCP budget.
- **No preferences**: the output stays byte-identical to main.

### Scope extension 2: facet rules and discovery (implementer)

`formats` was migrated to `rules` with `field: "format"` and generalized: fields `format`, `venue`, `day`, `topic`, `area`, `industry`, `role`; actions `only`, `prefer`, `avoid`, `exclude`; each rule optionally scoped to a level range. `only` is a union within a field and an intersection across fields, and a session with no value for the field is removed. `prefer`/`avoid`: the first matching rule decides within a field, the effects add across fields (+1/-1) and the sum is the tier. A `why` names every preference that moved a session ("a chalk talk at MGM Grand, which you prefer"; both directions when fields disagree). A value is checked against its field's vocabulary (any case, exact before unique prefix); one that does not resolve is an error listing the values that contain what was typed (else the commonest) and pointing at `list_filters`.

Discovery: `listFilters` in `src/catalog/filters.ts`, MCP `list_filters`, CLI `catalog filters [--field] [--json]`. Counts are distinct talks (a repeat's sittings count once per value), most first, levels in order. With no field each field lists 40 values (MCP) or 15 (CLI text) and `more` says how many were left out; with a field the whole list, halved until the MCP response fits 30 KB. Real catalog: all fields 40 values per field in the MCP shape is well under budget, and `--field topic` in full is the largest list.

**Checks, 7 profiles.** `--only venue:MGM Grand`: every result of every lens is at MGM Grand (28 lists, 0 violations); map counts drop on 7/7 profiles; map counts equal focus totals under the same rule on 258/258 topic-goal pairs. No preferences: byte-identical to main, 70/70. The levels and format-ordering checks above were re-run after the migration with the same results (400-500: 0 range violations, 258/258; chalk and avoided-breakout tiers 28/28, demoted last 28/28). Within-tier order of the All lens differs on 6 of 28 because the cap runs after the tier.

**Sabotage.** 35 more mutants (facet admission, union/intersection, level scope, first-rule-per-field, sum across fields, value resolution, notes, descriptions, `listFilters` distinct counting/ordering/limit/unknown field, CLI parsing, the `catalog filters` text, MCP `list_filters` default and budget loop), each red on a named test after one fix (a "closest values" test that the commonest-first fallback also satisfied).
