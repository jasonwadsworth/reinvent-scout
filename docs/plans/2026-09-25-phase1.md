# reinvent-helper — Phase 1 implementation plan

Written 2026-09-25. Target: hackathon deadline 2026-11-06.

Phase 1 is the vertical slice that proves the product: **sign in once -> sync catalog -> profile a repo
-> get matched candidates -> favorite them -> read the schedule back**, reachable from both a CLI and a
local MCP server, driven by an agent skill.

---

## Decisions made (assumptions the reviewer should check)

These were ambiguous in the brief. Each has a defensible default; none needs to block work.

1. **CLI framework: `commander`.** Zero runtime dependencies, mature nested-subcommand support
   (`auth login`, `skill install`), good `--help` generation. Node's built-in `node:util parseArgs`
   would mean hand-rolling subcommand routing and help text for no benefit. `yargs` pulls a
   dependency tree we do not need.
2. **MCP: `@modelcontextprotocol/sdk`** over stdio, as directed. It takes Zod schemas for tool input,
   so **`zod`** is a transitive requirement and we use it for config validation too rather than adding
   a second validator.
3. **No HTTP client dependency.** Node 24 has global `fetch`. The API client takes `fetch` by
   injection, so tests use a fake and never touch the network.
4. **No search-library dependency.** The match score is a weighted feature sum (exact service match
   dominates, text overlap is a tiebreaker) and **every candidate must carry the reasons that scored
   it**, which an off-the-shelf index cannot produce. A hand-rolled deterministic scorer (~120 LOC) is
   the right size and is explainable, which the article needs.
5. **No `open` dependency.** A ~15-line platform launcher (`open` / `xdg-open` / `start`) with an
   injected spawner, and the URL is always printed as a fallback, matching the working spike.
6. **Callback host is `localhost`, not `127.0.0.1`.** The spike proved `http://localhost:8484/callback`
   is accepted by the authorization server, and redirect matching is exact. The HTTP server binds the
   same hostname so browser resolution cannot diverge from the bind address.
7. **Kiro skill directory is not guessed.** `skill install` ships a built-in target for Claude Code
   (`~/.claude/skills/<name>/`) and a `--dir <path>` flag that covers Kiro and anything else. We cannot
   verify Kiro's path from here, and shipping a wrong hard-coded path is worse than a documented flag.
8. **Write pacing lands in PR 3, not PR 1.** The write quota is 30 session-units/min and only the
   favorites path spends it. Per YAGNI the pacer lives next to its only caller instead of being built
   speculatively into the client.
9. **`includeAbstracts` defaults to true on sync.** Abstracts are the main text signal for matching.
   They stay on disk and are stripped from every agent-facing output; `--no-abstracts` is available for
   a slim sync.
10. **Store root is `~/.reinvent-helper/`**, overridable by `REINVENT_HELPER_HOME` so tests never touch
    a real home directory. Directory `0700`, `tokens.json` `0600`.
11. **Phase 1 ships the Explain lens only.** Fix (Well-Architected) and Next level (migration paths)
    are out of scope but the `Lens` type and the `Reason` union are shaped to take them without a
    rewrite. See "Seams for later phases".
12. **Reservations are out.** Writes open 2026-10-08 and return 409 before then; reservations are
    phase 2. Favorites work today.

### Catalog facts confirmed against the real 2,043-session pull

Grounding for the tasks below; all verified against the Sep 25 pull, not assumed.

| Fact | Value |
|---|---|
| Sessions / pages | 2,043 in 9 pages of 250 |
| `venue` present | 1,146 of 2,043 |
| `venue` missing | 897 — 522 Wynn/Encore, 328 Caesars Palace, 47 with no room at all |
| `room` / `sessionTime` missing | 47 sessions, the same 47 |
| `level` missing | 1 session |
| `isReservable` true | 0 (opens 2026-10-06) |
| `seatAvailability` present | 0 |
| Distinct service names | 170 |
| Session types | 10 |

Two quirks drive real code:

- **Venue derivation.** When `venue` is present the room string starts with `Level N`. When `venue` is
  absent the room string starts with the venue name itself (`Wynn/Encore | ...`, `Caesars Palace | ...`).
  So: `venue ?? firstPipeSegment(room) if it matches a known venue ?? null`.
- **`sessionTime` has no `timezone` key in practice** even though the schema allows one. All times are
  Las Vegas local. The index stores `date`, `time`, `lengthMinutes` and leaves timezone handling to the
  on-site phase; it must not assume the key exists.

Also load-bearing: `AssociateFavorites` accepts **at most 10 `sessionIds` per call**, and a `200`
response can still contain per-session refusals in `result.failed`.

## PR split

Three PRs. **Split reason: size** — phase 1 is roughly 2,400 substantive LOC excluding fixtures and
generated files, well over the ~1,000 LOC threshold. PR 1 additionally satisfies **genuine layer
independence**: it ships a usable "sign in and search the catalog offline" tool that we would merge
even if the rest of phase 1 were cancelled.

| PR | Scope | Ships on its own |
|---|---|---|
| 1 | Scaffold, auth, API client, catalog sync + index, local catalog query | Sign in, sync, search the catalog offline |
| 2 | Repo profiler, taxonomy mapping, matcher, `profile` + `match` | Point it at a repo, get scored sessions with evidence |
| 3 | Schedule read/write, MCP server, skill v1, `skill install/update`, final README | The agent-driven end-to-end flow |

Merge order is strictly 1 -> 2 -> 3; each merges to `main` green before the next starts. Every PR
leaves the CLI in a state where **every command listed in `--help` works end to end** — no command is
registered before its implementation lands (global rule: UI visibility equals feature availability).

PR bodies use `Part N of 3 for phase 1`; only PR 3 closes the phase-1 tracking issue.

## Repo-wide conventions (established in PR 1, task 1)

- TypeScript strict, ESM (`"type": "module"`), `moduleResolution: "bundler"`, target `es2023`, Node 24.
- Commands: `npm test` (vitest run), `npm run typecheck` (`tsc --noEmit`), `npm run lint`
  (eslint + typescript-eslint), `npm run build` (`tsc`), `npm run check` (all four).
- Every task's run steps below use these exact commands.
- `src/core/**` holds the logic. `src/cli/**` and `src/mcp/**` are thin adapters over it so the two
  surfaces cannot drift. Business logic in an adapter is a review rejection.
- Every module that touches time, randomness, the filesystem root, the network, or the process takes
  it by injection. No test may hit the network or the real home directory.
- No token, `id_token`, refresh token, authorization code, or PKCE verifier is ever logged, printed,
  or included in an error message. A test asserts this for the auth module.

## Risks

1. **Catalog shape changes before the event.** The index builder tolerates every missing field and the
   schema version forces a rebuild, but a renamed field would break silently. Mitigation: `catalog sync`

## Implementation notes (appended during Part 1 build)

1. **TypeScript pinned to `~5.9.3`, not latest (Task 1).** The registry's latest `typescript` is
   `7.0.2` (the native/tsc-go line), but `typescript-eslint@8.70.1` declares a peer range of
   `>=4.8.4 <6.1.0`. Installing latest would break lint. 5.9.3 is the newest release inside that range.
2. **`engines.node` set to `>=22.13.0`, not the bare `>=22` from the lead's amendment (Task 1).** The
   actual floor across our chosen deps is higher than 22.0: `vitest@5` requires `^22.12.0`,
   `eslint@10` requires `^22.13.0`, and `commander@15` requires `>=22.12.0`. `>=22.13.0` is the real
   minimum that installs cleanly; a bare `>=22` would let someone on Node 22.0 install and fail at
   `npm install` or worse, at runtime.
3. **`tsconfig.json` uses `module: "esnext"`, not `"nodenext"`, alongside `moduleResolution: "bundler"`
   (Task 1).** TypeScript rejects `moduleResolution: "bundler"` paired with `module: "nodenext"` (the
   pairing is invalid). Since the plan is explicit about `moduleResolution: "bundler"`, `module` was
   changed to `"esnext"` instead. Because `bundler` resolution does not require explicit file
   extensions on relative imports at compile time, but the compiled output is executed directly by
   Node's ESM loader (which does require them), every relative import in `src/**` is written with an
   explicit `.js` extension (even though the source files are `.ts`) — this is the standard TS+ESM
   convention and was verified end-to-end: `node dist/cli/main.js --version` runs correctly after
   `npm run build`.
4. **Windows browser launch uses `rundll32 url.dll,FileProtocolHandler <url>`, not `cmd /c start`
   (Task 8).** `cmd /c start "" <url>` only opens correctly if the URL survives cmd.exe's own
   command-line re-parsing, which treats an unescaped `&` — present in every OAuth authorize URL —
   as a command separator regardless of how Node quoted the argument for `CreateProcess`. Rather
   than hand-build a `windowsVerbatimArguments` string whose correctness can't be checked without a
   real Windows machine, the launcher spawns `rundll32` directly (no shell in between, so nothing in
   the URL needs escaping) — the standard way to open a URL in the system default browser from a
   non-shell process. **This entire win32 code path is untested on real Windows hardware** — only
   the argv it produces is pinned by a test (`tests/auth/browser.test.ts`). If it's wrong on some
   Windows configuration, the printed authorize URL (`src/auth/login.ts` always prints it as a
   fallback, per decision 5) is how a Windows user completes login regardless.
5. **`isStoredTokens` rejects non-finite `expiresIn`/`obtainedAt`, not just non-numbers (Task 6).**
   `typeof value === "number"` alone accepts `NaN` and `+/-Infinity`. This isn't only a defense
   against a hand-edited `tokens.json`: `1e400` is valid JSON number syntax that `JSON.parse`
   evaluates to `Infinity`, so a *machine-generated* file can carry this value with no human
   involved. Left unchecked, an `Infinity` `obtainedAt` makes `isAccessTokenExpired` compute
   `expiresAt = Infinity`, so the token reports itself as never expiring — a session that looks
   permanently valid and silently never refreshes, which is a nasty one to debug from the
   symptom. The same read-path hardening was applied to `src/catalog/store.ts`'s `readJsonFile`
   (a corrupt `meta.json` is now reported as `{ status: "stale", reason: "corrupt" }` rather than
   throwing a raw `SyntaxError` out of `getCatalogState`), since it had the identical
   exists-then-read defect.

- **`zod` removed from part 1's dependencies.** Decision 2 anticipated it for the MCP SDK's tool
  schemas, but nothing in part 1 imports it, and the independent PR review flagged an unused
  runtime dependency. Part 3 adds it back when the MCP server actually needs it.

## Implementation notes (appended during Part 2 build)

1. **The service alias index is not persisted through `store.ts` (task 1).** The file list said
   "Modify: `src/catalog/store.ts` -- expose the alias index alongside the index," but
   `buildServiceAliasIndex` (`src/catalog/service-aliases.ts`) is built in memory from the loaded
   index's service names instead, with no new file, schema version, or staleness question of its
   own. Rebuilding an index of a few hundred short strings costs microseconds (0.35ms measured
   against all 170 real service names), so persisting it would only add a second thing that could
   go stale relative to `index.json` for no measurable benefit. Reviewer and lead approved this
   deviation explicitly. The caller builds the index once per run (e.g. once per `match`
   invocation) and passes it down -- never once per candidate session, which at 2,043 sessions
   would turn a microsecond cost into a real one against part 2's two-second acceptance bar.
2. **A colliding service alias degrades instead of throwing (task 1).** The task 1 write-up
   originally called for `buildServiceAliasIndex` to throw at build time when two canonical names
   derive the same alias. Lead decision after task 1 landed: an alias collision must never make
   the `match` command unusable for every user. `buildServiceAliasIndex` now drops a colliding
   alias (`resolve` returns `null` for it, exactly as if nothing had derived it) and reports it in
   a new `collisions: ServiceAliasCollision[]` field instead of throwing; each colliding service's
   own full display name is unaffected, since two different services essentially never share the
   exact same full name. The reason: a rename on AWS's side that happens to collide under these
   rules must degrade one alias -- detection for that service falls back to topic and text
   signals -- not break every candidate list for every repo until a code fix ships. `match`
   surfaces `collisions` as a warning in its result (never printed to stdout on its own), the same
   pattern `catalog sync` already uses for a total-count mismatch.
3. **One shared skip-directory/skip-file policy, not one per module (task 4).** `walkRepo`'s
   `SKIPPED_DIRECTORY_NAMES`, `SKIPPED_FILE_NAMES` and `SKIPPED_FILE_EXTENSIONS`
   (`src/profile/walk.ts`) are exported and every detector that filters paths on its own account
   (starting with `detectManifests`) imports and uses them, rather than hard-coding its own
   subset. Lead decision: since a detector is a pure function over a file list, independent of
   `walkRepo`, and is deliberately usable with a file list sourced some other way later (the
   plan's seam for GitHub issues as intent), it needs its own defense against a path a real walk
   would never have produced -- but two independently-maintained skip lists could silently drift
   apart, letting a detector "see" something (a `.venv` dependency, say) that a `walkRepo`-driven
   caller never would. Each detector's test suite that exercises this includes one case driven
   directly from the exported constant (`it.each([...SKIPPED_DIRECTORY_NAMES])`), so adding a name
   to the walker's policy automatically extends every detector's assertion instead of requiring a
   matching manual edit in each detector's test file.
4. **Every detector normalizes its keys through one shared `normalizeServiceKey` (tasks 5-6).**
   The same AWS API variant produces a different raw key per language: `@aws-sdk/client-bedrock-
   runtime` and `boto3.client("bedrock-runtime")` keep a hyphen, while the Go package and Java
   class name (`bedrockruntime`) can't carry one. Merging on a resolved catalog name instead
   (task 10) does not fully solve this -- a service with no catalog counterpart at all (SNS today)
   has no name to merge on -- so `src/profile/service-keys.ts` gains `normalizeServiceKey`:
   lowercase, strip every non-alphanumeric character, then apply a small `KEY_NORMALIZATION_
   OVERRIDES` table (distinct from `SERVICE_KEY_OVERRIDES`, which maps key -> catalog name) that
   collapses a handful of curated cross-language spelling variants (`bedrockruntime` -> `bedrock`,
   `sagemakerruntime` -> `sagemaker`) to one canonical key. Every detector that emits a service key
   calls this before returning it -- the only place a key's shape is decided -- so `profile.ts`
   can merge detections of the same service across languages *and* across detectors by key alone,
   which works for an unresolvable service exactly as well as a resolvable one. Removed
   `sdk-usage.ts`'s local `JS_CLIENT_KEY_OVERRIDES` (redundant once this exists). Added
   `"sagemaker-runtime": "Amazon SageMaker"` to `SERVICE_KEY_OVERRIDES` as defense-in-depth (a lead
   product decision: a repo calling SageMaker's inference-endpoint API uses SageMaker and should
   surface SageMaker sessions, the same call already made for Bedrock) -- in practice no detector
   emits that raw spelling anymore post-normalization, but a caller resolving a key directly still
   needs it, the way `catalog/service-aliases.test.ts`'s own tests do.

   The divergence turned out to be per-*detector*, not only per-language: `detectCdkUsage`
   naturally emits `"stepfunctions"` (from `aws-cdk-lib/aws-stepfunctions`) while `detectSdkUsage`
   naturally emits `"sfn"` (the Go SDK's package name) for the same service, and
   case/punctuation-stripping alone cannot unify two different words. `KEY_NORMALIZATION_
   OVERRIDES` gained `sfn -> stepfunctions`; `"stepfunctions"` was picked as canonical because two
   of the three code paths that touch this service already produce it and it resolves through the
   ordinary derivation rules with no override needed. Confirmed the alias step is genuinely
   load-bearing, not merely the character filter: a normalizer with the override table removed but
   the lowercase/strip-punctuation step intact still fails
   `tests/profile/detectors/service-key-agreement.test.ts`'s CDK-vs-SDK Step Functions test, which
   is exactly the case a character filter alone cannot pass.
5. **A `.json` CloudFormation/SAM template is parsed exactly; `.yaml`/`.yml` stays line-scanned
   (task 7).** The line-oriented `Type:` extraction (needed for YAML, where the plan forbids a
   parser dependency) has a real accuracy cost for JSON specifically: it assumes one key per line,
   so a minified, single-line JSON template silently loses every resource-type detection even
   though the file is still correctly classified as a template. Lead decision: since `JSON.parse`
   needs no dependency and JSON has no comments to be confused by, a `.json` file is parsed exactly
   and its resources read via `Resources[*].Type`, falling back to the same anchored line scanner
   only when parsing fails -- and a JSON parse failure is reported in a new
   `unreadableTemplates: UnreadableTemplate[]` field (carrying the parser's own error message)
   rather than silently relying on whatever the fallback scan happens to recover. This removes a
   silent under-detection instead of just documenting it as a known limitation.
6. **The Terraform detector's "known key set" is derived from the catalog, not a hand-written list

   specifying its source; the first pass used an 18-entry hand-written

   Redshift, Kinesis, SageMaker, Glue, Athena or EventBridge with zero service signal, while the

   `"elasticacheserverless"` (not `"elasticache"`) -- the lead's call, since a session tagged for

   which literal key the plan's own sentence and this repo's original test named. A small
   `TERRAFORM_PREFIX_OVERRIDES` (key -> key, not key -> catalog name) remains for the handful of

7. **The deterministic repo profiler (walker, four detectors, pattern derivation) is removed;

   In short: every review round on tasks 3-8 found another false-positive shape a line-oriented
   detector had to be specifically hardened against -- comments, string values, ambiguous
   provider-name prefixes, a hand-written key vocabulary that couldn't keep pace with the
   catalog's 170 real service names -- and an LLM reading the repository characterizes it better
   than rules over its text ever will, at a cost (tokens) that anyone using this tool has already
   chosen to pay. `src/profile/walk.ts`, `src/profile/detectors/**`, `src/profile/detectable-
   file.ts`, `tests/fixtures/repos/**`, and every test for all of the above were deleted in Task
   R1, along with the fixture-repo exclusions from `tsconfig.tests.json` and `eslint.config.js`
   they required. `src/catalog/service-aliases.ts` and `src/profile/service-keys.ts` (including

   naturally would, which is a *superset* of the syntactic forms the deleted detectors used to

8. **Resolving an agent-authored service name needs a wrapper-affix list plus segment-based
   longest-prefix matching, not `normalizeServiceKey` alone (task R2).** R2's own named test case,
   `"@aws-sdk/client-dynamodb"` resolving like `"dynamodb"`, doesn't work through plain
   punctuation-stripping: the affix glues onto the service name (`"awssdkclientdynamodb"`), which
   resolves to nothing. Lead decision: `service-keys.ts` gained an ordered `AFFIXES_TO_STRIP` list
   (`"@aws-sdk/client-"`, `"aws-sdk-"`, `"aws-cdk-lib/aws-"`, `"aws_cdk.aws_"`, `"aws_"`,
   `"software.amazon.awssdk.services."`, `"github.com/aws/aws-sdk-go-v2/service/"`) and an exported
   `stripKnownAffix`, applied inside `normalizeServiceKey` before the existing case/punctuation
   step. Order matters: `"aws_cdk.aws_"` must be checked before the shorter `"aws_"` it starts
   with, confirmed by a dedicated test and a sabotage swapping the order.

   A stripped affix alone doesn't handle Terraform's own `aws_<service>_<resource>` shape --
   `"aws_dynamodb_table"` still needs the `_table` resource suffix separated from the service.
   Rather than a second rule guessing where that boundary is, `profile.ts` gained
   `resolveServiceName`: split the affix-stripped remainder into segments on `-`/`_` (never
   mid-token) and try progressively shorter segment-joins against the catalog, longest first. This
   also settles the same "which is more specific wins" question the removed Terraform detector
   raised (see item 6): the catalog carries both `"Amazon ElastiCache"` and `"Amazon ElastiCache
   Serverless"`, and trying the longest candidate first is what resolves
   `"aws_elasticache_serverless_cache"` to the more specific one -- confirmed by a test built so
   the two orders give different answers (most names, `aws_dynamodb_table` included, resolve
   identically either way and would prove nothing about ordering). A name with no catalog
   counterpart at all (`sns`, or `aws_sns_topic` once stripped) is confirmed to stay unresolved
   rather than being rescued by over-eager shortening.

   Follow-up found by the reviewer against the real 170-name catalog: applying segment shortening
   to *every* name, not just one a known affix was stripped from, produced real false positives --
   `"lambda-labs-gpu"` (a GPU hosting product) shortened down to `"lambda"` and wrongly resolved to
   AWS Lambda, and `"athena-health"` (a healthcare company) did the same for Amazon Athena.
   `resolveServiceName` now gates segment shortening on `stripKnownAffix` having actually changed
   the input: a name with no affix to strip is resolved as a single candidate and stops there.
   Verified this keeps every correct resolution (all seven `dynamodb` spellings, `aws_dynamodb_
   table`, `aws_elasticache_serverless_cache`, `sfn`, `bedrock-runtime`, `sagemaker-runtime`,
   plain names like `"Amazon DynamoDB Streams"`) while eliminating the false positives, against
   the real catalog snapshot before committing the fix.
9. **`scoreSession`'s text scoring drops document-length normalization entirely (task R4/11).**
   A first version divided the body-term score by the record's own total body-term count, meant to
   stop a long abstract from outscoring a short precise title just by having more text to
   accumulate matches over. This is degenerate for a document that repeats one relevant term many
   times with little else around it: its self-referential "length" grows exactly as fast as its
   raw score, so the normalized score actually *falls* as the term repeats more, the opposite of
   merely saturating -- confirmed by the scorer's own saturation test, which failed exactly that
   way with the normalization in place. Real BM25 avoids this because it normalizes against a
   corpus-wide average length, not a document's own; this scorer has no corpus statistics to draw
   on. Removed length normalization; per-term saturation (`tf / (tf + 1.5)`) combined with the
   existing 3x title-over-body weighting is sufficient on its own for a short precise title to
   outscore a long, unrelated-but-overlapping abstract, since a body term's contribution can never
   exceed its own weight regardless of repetition. The reviewer independently confirmed removing
   normalization costs nothing: scoring all 60 fixture sessions against a realistic query, the top
   eight results' abstracts average shorter than the corpus mean, so the ranking isn't biased
   toward long documents.

    23/24's acronym exception keys on original casing, and both `catalog/query.ts` and
    `match/score.ts` tokenize a query through the exact same `tokenize` function that builds the
    index -- so a lowercase `s3` or `ai` in a search query or a profile's free text was silently
    dropped even though the index itself carries the term (from the catalog's own capitalized
    source copy). Reproduced: `catalog search s3` returned nothing while `catalog search S3` found
    ANT314. This was a real regression in `catalog search`, a command part 1 already shipped and
    which was case-insensitive everywhere else -- not something specific to profile authoring, so
    routing it to Part 3 as authoring guidance (an earlier draft of this note did exactly that) was
    the wrong fix. Corrected: `tokenize` gained a `keepShortTokens` option that skips the length/
    acronym filter entirely, used by `catalog/query.ts`'s search and `match/score.ts`'s query-text
    scoring, but *not* by `buildIndexRecord` -- the filter still keeps corpus noise out of what gets
    indexed, it just no longer also constrains how a query is allowed to spell a real term that may
    already be there. A short query term absent from the index simply matches nothing, at no
    precision cost. Removed the "write acronyms in caps" line this bug had added to the Part 3
    profiling carry-over notes, since it's no longer true: a profile can write "ai" or "AI"
    interchangeably now. Three tests: `tokenize` with `keepShortTokens: true` keeps "ai"/"s3" that
    the default drops; `catalog search "s3"` and `"S3"` return identical results against the real
    fixture's ANT314; a profile note reading "we use ai heavily" matches INV501, indexed from its
    own capitalized "AtoZ AI Co-Scientist" title.
30. **`LensProfile.typeWeights` converted to a `Map` (fresh pr-reviewer finding, MEDIUM -- the
    one prototype-key hazard this codebase's own established pattern missed).** `record.type` comes
    straight from the catalog API, and `typeWeights` was a plain object literal, so a session typed
    `"constructor"` read the inherited `Object.prototype.constructor` function from a bracket lookup
    instead of `undefined`, passed the `!== undefined` "is this a real bonus" check, and corrupted
    that session's score: `score += formatBonus` on a function operand coerces to string
    concatenation (confirmed directly: `50 + {}.constructor` produces `"50function Object() {
    [native code] }"`, not a number), and the *later* rounding step's `value * 100` then coerces
    that already-corrupted string to `NaN`, which `JSON.stringify` serializes as `null` -- matching
    the reviewer's exact reproduction. This is precisely the hazard `tokenize`'s term-frequency maps
    and both service-key override tables were already fixed for; `typeWeights` was the one place in
    the new code that reintroduced it. Fixed by making `typeWeights` a `ReadonlyMap<string, number>`
    and switching the one read site (`match.ts`) to `.get()`. One test: a session typed
    `"constructor"` under a lens that grants a real format bonus to other types scores a real
    number, not `NaN`, and gets no format reason (correctly, since `"constructor"` was never a real
    key). Sabotage-confirmed: reverting to a plain object literal turns exactly this test red.
31. **`match --include-abstracts` without `--json` was a silent no-op (fresh pr-reviewer finding,
    MEDIUM).** Both the with- and without-abstracts branches' human-readable output called the same

    built and then discarded on that path. `formatCandidateWithReasons` now takes an optional

32. **`catalog show <base code>` resolves, listing the other sittings (fresh pr-reviewer finding,

## Part 2 rescoped (lead decision, 2026-09-26)

**Decision (Jason):** the repo profile is authored by the agent running the skill, not by
deterministic detectors. The detector code is fragile (every review round found another
false-positive shape: comments, prefixes, substrings, hand-listed prefixes) and an LLM reading the
code characterizes a repository better than rules over its text. Anyone using this tool has chosen
to spend tokens on it; the CLI does not need a no-LLM profiling path. The CLI keeps everything that
is genuinely deterministic: catalog sync and index, service-name resolution, scoring, matching,
schedule writes, and the MCP surface.

The evidence discipline moves from the detectors to the schema.

## Implementation notes (appended during Part 3 build)

1. **`match_sessions`'s response size, measured against the real catalog, not the fixture (task
   5).** The 61-session fixture used throughout the committed test suite cannot produce a response
   anywhere near the 30 KB budget the plan's task 5 acceptance criterion names -- confirmed
   directly: the same profile and limit that measured ~40 KB against the real 2,043-session
   snapshot (`~/reinvent-scout-snapshots/catalog-2026-09-25.json`, not committed) stayed under 2 KB
   against the fixture. The reviewer's explicit ask to measure at the default limit against the
   real snapshot caught this before it shipped.
   The MCP candidate shape started as the CLI's own full `toPublicIndexRecord` per candidate (task
   5's first draft). Against the real catalog with a realistic five-service profile (Lambda,
   DynamoDB, Step Functions, S3, Bedrock -- an ordinary serverless-AI stack, not a contrived worst
   case), the default-limit-25 response measured ~40 KB, well over budget. Trimmed to a leaner
   shape (`toLeanCandidate` in `src/mcp/tools.ts`: drops fields `offerings` already duplicates --
   `abbreviation`/`level`/`venue`/`room`/`startDate`/`startTime` -- plus every taxonomy array):
   got the *content text* to ~28 KB, but the full `CallToolResult` envelope (what the budget and
   the size test both actually measure) was still ~31 KB. Dropped `type` and `services` too
   (`services` is redundant with what `reasons` already names explicitly; `type` is a genuine, if
   smaller, loss -- flagged rather than silently cut) to reach ~28.5 KB with real headroom at the
   default limit. The cap of 50, however, still measured ~52 KB even with the trimmed shape --
   the budget held at the default limit but not at the cap, an open question raised to the lead
   rather than resolved unilaterally (lowering an explicit brief number, or accepting an
   inconsistent guarantee, are both real product decisions).
2. **Lead decision on the cap-vs-budget question (following note 1): the 30 KB budget is a hard
   guarantee at every limit, including the cap, enforced mechanically at serialization time rather
   than by trimming the candidate shape further.** Default 25 and cap 50 stand unchanged (a
   profile naming many services can make even a moderate candidate count exceed the budget, not
   just a large `limit` -- the mechanism has to hold regardless of *why* the response got big).
   `buildMatchResponse` in `src/mcp/tools.ts` serializes candidates in ranked order, checking each
   prospective response as a whole (never a partially-serialized candidate) against the budget,
   and stops before adding one that would exceed it. The response gained `truncated`, `returned`,
   `requested`, and (only when `truncated`) a one-line `hint` ("ask again with a smaller limit or a
   narrower lens"). `reasons` and `offerings` stay intact on every included candidate --
   explainability is the substance a truncated response still has to deliver.
   Tested against a deliberately synthetic catalog (twenty long, distinct service names shared by
   every session, each producing its own "service" reason -- the real catalog and the fixture both
   under-provoke this, so the test manufactures a scenario that measured ~268 KB unbudgeted, to
   actually exercise the mechanism rather than assume it): a request for 50 against that catalog
   returns fewer, `truncated: true`, staying under 30 KB; the fixture-catalog request (already
   small) returns everything with `truncated: false` and no `hint` field at all. Re-verified
   against the real snapshot after the fix: the default limit stays untruncated at ~28.6 KB, and
   the cap of 50 now truncates to 26 candidates at ~29.6 KB -- the budget holds at both limits, not
   just the default.
   Sabotage-confirmed independently: disabling the truncation branch entirely (always returning
   every candidate) reproduces the original ~268 KB overage, caught by the truncation test's size
   assertion. Measuring only the inner content text instead of the full envelope (the JSON-RPC
   wrapper's own overhead) let a response through at ~32 KB that the mechanism believed was under
   budget -- confirming the wrapper-inclusive measurement is load-bearing, not defensive
   over-engineering; the two checks are genuinely different properties, not one written twice.
